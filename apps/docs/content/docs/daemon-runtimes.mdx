In Multica, [agents](/agents) do **not** run on our servers — they run on your own machine, driven by one machine-wide **Computer resident** that invokes the [AI coding tools](/providers) installed locally. The Multica server coordinates issues, tasks, and **runtimes** (runtime = one Workspace connection × one local AI coding tool).

This structure is the biggest difference between Multica and Linear / Jira: **your API keys, toolchain, and code directories stay on your machine** — the Multica server never sees any of them. That means "my agent isn't working" is almost always a local problem — the Computer isn't running, an AI tool isn't installed, or a key has expired. Check locally first; see [Troubleshooting](/troubleshooting) for a guide.

## Starting the Computer

The Computer is part of the Multica CLI. First connect a Workspace, then control the same resident from any terminal:

```bash
multica setup /my-workspace
multica computer start
```

On startup it does four things:

1. Reads the credentials saved when you logged in
2. Detects AI coding tools installed on your `PATH` (7 built-in: [Claude Code](/providers#claude-code), [Codex](/providers#codex), [Cursor](/providers#cursor), [Grok](/providers#grok), [Kiro CLI](/providers#kiro-cli), [OpenCode](/providers#opencode), [Pi](/providers#pi))
3. Registers itself with the server, along with a runtime for each detected tool
4. Keeps **polling every 3 seconds** for tasks to pick up, and **sends a heartbeat every 15 seconds**

Common commands:

| Command | Purpose |
|---|---|
| `multica computer start [/<workspace>]` | Start the one detached resident |
| `multica computer stop` | Stop it gracefully |
| `multica computer restart [/<workspace>]` | Restart the same resident |
| `multica computer status` | Show environment, fixed package source, identity, and connections |
| `multica computer logs [/<workspace>]` | Show logs (add `-f` to follow) |
| `multica computer doctor [/<workspace>]` | Diagnose local state without changing it |

Full CLI reference in [CLI commands](/cli).

`multica daemon ...` is a hidden compatibility alias. New setup and operations use `multica computer ...`.

## Why one machine has multiple runtimes

A runtime is not a server and not a container — it is the combination of "**one explicit Workspace connection × one AI coding tool**". For example, your Computer connects a MacBook to two Workspaces and finds Claude Code plus Codex. Multica then registers 4 runtimes:

Key points:

- **One Computer can map to multiple runtimes** — one per combination of installed tool and explicitly connected Workspace
- **The same Computer, environment, Workspace, and tool produces exactly one runtime** — restarting never creates duplicate records
- The **Runtimes** page in the Multica UI lists these rows

## When a runtime is marked offline

Multica uses heartbeats to decide whether a runtime is online. Three key numbers:

| Event | Threshold |
|---|---|
| Computer heartbeat frequency | Every **15 seconds** |
| Marked as missing | No heartbeat for **45 seconds** (3 missed beats) |
| Auto-deleted | Missing with no associated agents for over **7 days** |

Missing is not permanent — as soon as the Computer sends another heartbeat it returns to online, and the runtime record is preserved. Restarting the Computer does not lose runtimes.

<Callout type="warning">
**Tasks running on a missing runtime are marked as failed** (failure reason `runtime_offline`). For retryable sources (issues, chat), Multica automatically requeues them. See [Tasks → Which failures retry automatically](/tasks#which-failures-retry-automatically-which-dont).
</Callout>

## How many tasks can run in parallel

Multica enforces concurrency limits at two layers:

- **Computer resident layer**: **20 concurrent tasks** by default (tunable via the internal env var `MULTICA_DAEMON_MAX_CONCURRENT_TASKS`)
- **Agent layer**: **6 concurrent tasks per agent** by default (configured per-agent)

The tighter of the two wins. If your Computer is already running 20 tasks, new tasks wait even if an agent still has headroom.

If you see tasks stuck in `queued` without moving to `dispatched`, one of these two limits is usually saturated.

## What happens to in-flight tasks after a Computer crash

When the Computer resident crashes or is force-killed, its tasks are left in `dispatched` or `running`. On the next start, the Computer tells the server that those tasks no longer have a live owner. The server flips them to `failed` with reason `runtime_recovery`; retryable sources are automatically requeued.

Even if this step fails due to a network issue, there's a server-side scan **every 30 seconds** as a backstop: any runtime without a heartbeat for over 45 seconds is marked missing, and its tasks are reclaimed along with it.

## Troubleshooting agents that aren't working

When you hit a "my agent isn't working" problem, run this three-step checklist first:

1. Run `multica computer status` — confirm the resident is running in the expected environment
2. Run `multica computer logs -f` — check for errors
3. Open the **Runtimes** page in the Multica UI — confirm your runtime shows "online"

More scenarios in [Troubleshooting](/troubleshooting).
