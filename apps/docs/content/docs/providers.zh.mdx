Multica 内置支持 **7 款 AI 编程工具**。它们都实现了同一套接口——排队、派发、执行、结果回传，所以你可以从 Multica 的同一个看板上指挥任意一款。**但它们在能力细节上差异很大**：会话恢复是否真用、是否支持 MCP、skill 文件该放在哪里、模型怎么选。这一页是完整对照。

创建智能体时挑选工具的指引见 [创建和配置智能体](/agents-create)。

## 能力对照矩阵

| 工具 | 厂商 | 会话恢复 | MCP | Skill 注入路径 | 模型选择 |
|---|---|---|---|---|---|
| **Claude Code** | Anthropic | ✅ | ✅ | `.claude/skills/` | 静态 + flag |
| **Codex** | OpenAI | ⚠️ 代码存在但不可达 | ✅ | `$CODEX_HOME/skills/` | 静态 |
| **Cursor** | Anysphere | ⚠️ 代码存在但不可用 | ✅ | `.cursor/skills/` | 动态发现 |
| **Grok** | xAI | ✅ | ❌ | `.grok/skills/` | 动态发现 |
| **Kiro CLI** | Amazon | ✅ | ✅ | `.kiro/skills/` | 动态发现 |
| **OpenCode** | SST | ✅ | ✅ | `.opencode/skills/` | 动态发现 + variant |
| **Pi** | Inflection AI | ✅（session 为文件路径）| ✅ | `.pi/skills/` | 动态发现 |

## 每款工具的定位

### Claude Code

Anthropic 出品。**新手首选**——功能最完整：会话恢复真的能用，会读 MCP 配置，还支持 `--max-turns`、`--append-system-prompt` 这类微调 flag。需要 Anthropic API key。

### Codex

OpenAI 出品。用 JSON-RPC 2.0，状态更强，审批粒度更细（`exec_command` 和 `patch_apply` 可手动批准）。MCP 配置会落到单次任务的 `$CODEX_HOME/config.toml`。**会话恢复代码存在但当前走不到**——如果需要 resume，选 Claude Code 或 ACP 家族。

### Cursor

Anysphere 出品，Cursor 编辑器的 CLI 对应物。**会话恢复代码存在但实际不可用**——Cursor CLI 事件流不回传 session ID，你传的 resume 值永远无效。需要 resume 就换别的。**MCP 真用**：Multica 把智能体的 `mcp_config` 写进 `{workdir}/.cursor/mcp.json`，并带 `--approve-mcps` 启动，避免无头 daemon 跑在审批提示上卡住。

### Grok

xAI 出品。CLI 二进制名是 `grok`（产品名：Grok Build）。走 ACP stdio。会话恢复走 ACP session，模型从 runtime 动态发现，skill 落在 `.grok/skills/`。**不转发 MCP**——Multica 会藏掉这个 provider 的 MCP 页签，避免存了配置却静默无效。

### Kiro CLI

Amazon 出品。通过 `kiro-cli acp` 走 ACP over stdio。会话恢复走 ACP `session/load`，MCP 配置走 ACP `mcpServers`，模型选择走 `session/set_model`，skill 复制到 `.kiro/skills/` 做原生项目级发现。

### OpenCode

SST 出品，开源。会动态发现可用模型和 variant（扫描 CLI 自己的配置文件）。会话恢复可用，也会消费智能体的 `mcp_config`——Multica 通过 `OPENCODE_CONFIG_CONTENT` 环境变量内联注入，不改写任务工作目录里的 `opencode.json`（那个文件仍归智能体或用户）。模型暴露 variant 时，Multica 把它显示成 thinking 选择器，并通过 `opencode run --variant` 传过去。**适合想自己定制模型目录的人。**

### Pi

Inflection AI 出品，极简主义。**会话恢复机制特殊**——session ID 是磁盘上的文件路径（`~/.pi/...`），而不是字符串 ID。其他工具里，resume id 是 CLI 返回的字符串；Pi 里，resume id 就是会话文件本身。**MCP 真用**：通过 Pi 的 `--mcp-config` flag（与 Multica 存的 Claude 风格 JSON 相同）。

## 会话恢复：谁真的支持

会话恢复的机制在 [执行任务](/tasks#任务能接着上次的上下文继续吗) 里讲过。这里按工具列**精确现状**：

| 状态 | 工具 | 含义 |
|---|---|---|
| ✅ 真用 | Claude Code、Grok、Kiro CLI、OpenCode、Pi | 传 resume id，会从上次上下文接着继续 |
| ⚠️ 代码存在但不可达 | Codex、Cursor | 代码里有 resume 路径但实际走不到（Codex 静默回落、Cursor session id 不回传）—— **当作不支持** |

**对你的决策**：如果工作流需要智能体在多次任务之间保持上下文（失败重试、手动重跑、对话式迭代），只选 ✅ 那一行的工具。

## MCP 配置：按工具不同

**7 款工具里有 6 款实际消费 `mcp_config`：Claude Code、Codex、Cursor、Kiro CLI、OpenCode、Pi**。Grok 会接收这个字段但**忽略**——不报错、不警告，只是配置不生效，所以 UI 会藏掉 MCP 页签。

各工具的接入方式不同：Claude Code 和 Pi 通过 `--mcp-config` 接收（Claude 还会加 `--strict-mcp-config`）；Cursor 写入 `{workdir}/.cursor/mcp.json` 并传 `--approve-mcps`；Codex 会把 daemon 管理的 `mcp_servers` block 写入单次任务的 `$CODEX_HOME/config.toml`；Kiro CLI 通过 ACP `mcpServers` 接收；OpenCode 通过 `OPENCODE_CONFIG_CONTENT` 环境变量内联接收。OpenCode 这条路径**不会**改写项目里的 `opencode.json`。

<Callout type="warning">
如果你在智能体配置里设置了 `mcp_config`，但选了矩阵 MCP 列没有标 ✅ 的工具，你的 MCP server 对这个智能体**没有效果**。MCP 集成是按工具实现的。
</Callout>

## skill 文件该放哪儿

每款工具用**自己**的 skill 发现路径。Multica 的守护进程在执行任务前把 workspace 的 skill 文件复制到对应路径下：

| 工具 | 路径 | 是否原生发现 |
|---|---|---|
| Claude Code | `.claude/skills/` | ✅ 原生 |
| Codex | `$CODEX_HOME/skills/` | ✅ 原生 |
| Cursor | `.cursor/skills/` | ✅ 原生 |
| Grok | `.grok/skills/` | ✅ 原生 |
| Kiro CLI | `.kiro/skills/` | ✅ 原生 |
| OpenCode | `.opencode/skills/` | ✅ 原生 |
| Pi | `.pi/skills/` | ✅ 原生 |

skill 的创建和使用详见 [技能](/skills)。
