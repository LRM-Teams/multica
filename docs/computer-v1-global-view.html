Multica Computer V1 · Issue #2484

一台电脑，一个 Computer，连接多个 Workspace

这份图从用户视角讲清楚：Computer 到底是什么、Workspace connection 为什么存在、测试和正式环境怎么切、为什么环境会自动带上正确的包，以及升级怎么不把正在工作的 Agent 弄乱。

先说人话：Computer 是这台电脑上的常驻“工头”；Workspace connection 是它拿到的某个团队的“门禁卡”。一个工头可以拿多张门禁卡，所以一台电脑当然可以给多个 Workspace 干活。
Computer 核心实现与测试已完成 腾讯测试环境与生产部署编排仍待基础设施落地 latest.json 仅兼容旧客户端

01 / 总模型

不要再把 Workspace 当成一台独占电脑

1

一个本机身份

同一个 OS 用户下只有一个 Computer identity。它放在机器级目录里，不随 Workspace 名字变化。

2

一个常驻进程

只有一个 resident 占有本机锁、健康端口和 PID。旧的 profile 参数不能偷偷启动第二个。

N

多条 Workspace connection

每条连接单独授权、可单独撤销。Workspace A 出问题不会顺手删掉 Workspace B。

关键边界：同一时刻，一个 resident 只连一个环境的一个服务 origin，但会同时服务该环境下的所有 Workspace。Production 和 Test 的连接都能保存；切环境时重启 resident，另一边的连接不会丢。

02 / Connection

Binding 是内部名；用户只需要知道“Workspace connection”

它实际保存什么

environment、不可变的 workspace_id、computer_id、服务 origin、可撤销 credential、接受时间和激活状态。

本地唯一键是 (environment, workspace_id)。slug 只是给人看的，改名不改变连接身份。

它不是什么

不是“把整台电脑绑定死给一个 Workspace”，不是一个额外进程，也不是一个 workspace 文件夹。

所以移除一条 connection，只是收回一张门禁卡，不是把工头开除，也不是把其他团队的门禁卡一起剪掉。

你担心的情况Computer V1 的答案
一个电脑两个 Workspace？可以，而且是标准路径；同环境下由一个 resident 同时服务。
Workspace 改名？不影响。身份看不可变 workspace_id，slug 只展示。
只退出 Workspace A？只撤销 A；B 的连接、Agent 和运行状态保留。
为什么以前会冲突？旧模型把 profile、daemon、Workspace 选择混在一起，容易把“配置切换”误当成“第二台 Computer”。V1 把机器身份和多 Workspace 授权拆开。
03 / 环境

环境和包是一组固定套餐，不让用户自由乱配

选择的环境连接的服务自动使用的包清单
Productionapi.leagent.me / www.leagent.mestable/computer/manifest.json
Testtest.leagent.me 或明确的腾讯云 HTTP(S) originpreview/computer/alpha.json

最重要的规则：用户只选环境。没有单独的 release_channel 配置，也没有 computer channel 命令。切到 Test 就一起换 preview 包；切回 Production 就一起换 stable 包。

第一次接环境：setup

Production 固定官方域名。Test 必须给完整 HTTP(S) origin；裸 IP、路径、账号密码、query 都会被拒绝。

multica setup /my-workspace

multica setup --environment test \
  --test-url https://test.leagent.me \
  /my-workspace

以后切环境：config use

两边的登录和 Workspace connections 都已保存后，只切当前环境，不再登录一次。

multica config use test
multica config use production
multica config show

配置文件大白话

{
  "active_environment": "test",
  "environments": {
    "production": { "server_url": "https://api.leagent.me", "token": "(已保存)" },
    "test": { "server_url": "https://test.leagent.me", "token": "(已保存)" }
  }
}

这里的 token 是人的登录会话；真正让 Computer 替某个 Workspace 执行任务的 credential 仍单独放在 ~/.multica/computer/bindings.json。两者职责不同，不混成一个万能凭证。

04 / Setup

Setup 不是“写个 URL 就算好了”

校验环境和 originProduction 固定官方地址；Test 严格检查用户提供的 origin。
登录并解析 Workspace把人类输入的 slug 解析成不可变 workspace_id。
服务端接受 Computer connection确认当前用户对该 Computer 和 Workspace 都有权限，签发可撤销执行凭证。
原子写入本机 connections以 (environment, workspace_id) upsert；重复 setup 是修复，不会制造副本。
启动或重启唯一 resident持有机器级 lease，领取新的 generation；并发 start 只能有一个赢家。
用在线证据验收必须看到 running + connected:true，且 environment、origin、Workspace 都一致。只有本地文件不算成功。

零 Agent 也能 setup 成功：验收看的是 Computer 是否真正连上服务，不要求 Workspace 里先有 Agent。

已经 setup 过以后，切环境发生什么

为什么这么麻烦？因为直接改 JSON 时，旧 resident 还可能继续从旧服务领任务；直接杀进程又会打断正在跑的 Agent。安全切换先关“新任务入口”，等手上的活做完，再换服务和包。失败就恢复原套餐。

06 / 移除

“移除 Connection”和“删除 Computer”必须是两个按钮

Remove Workspace connection

只撤销一个 Workspace 的执行凭证、服务端授权和本地连接记录。即使这个 Workspace 当前没有 runtime，也必须能撤销。

兄弟 Workspace connection 不变；这是日常操作。

Delete Computer permanently

是机器级危险操作。不能拿它代替“离开一个 Workspace”，UI 必须和前者分开表达。

这是不可逆意图；应要求明确确认。

最容易犯的错：看到某个 Workspace 不用了，就把整台 Computer 删除。V1 的语义是先移除那一条 Workspace connection。

07 / 发版

日常按环境自动选包；--version 只留给安装与排障

用户输入读取路径允许指向大白话
Production / 省略 / --version latest/computer/manifest.json只能是稳定 vX.Y.Z正式环境自动使用；也是全新安装的默认值。
Test / --version alpha/computer/alpha.jsonalpha.N、beta.N、rc.N测试环境自动使用；安装器可显式预装。
--version v0.5.0-rc.2/computer/0.5.0-rc.2/manifest.json只允许清单与精确版本一致钉死某一版，方便复现和回滚。
旧客户端/computer/latest.json与根 manifest.json 字节一致迁移期兼容别名；新安装器不会把它当主路径。

alpha.N

早期试验版，变化快，主要验证方向和基本可用性。

beta.N

功能基本齐，扩大测试面，重点找兼容与真实场景问题。

rc.N

Release Candidate，候选正式版；没有阻断问题就升稳定版。

别把安装参数当长期配置：--version 用于第一次安装、恢复和复现；Computer 正常运行后，由当前环境固定决定 stable 或 preview。Raft 也没有为 Multica 的清单命名背书。

# 默认稳定版
curl -fsSL https://cdn.leagent.me/computer/install.sh | bash

# 滚动预发布通道
curl -fsSL https://cdn.leagent.me/computer/install.sh | bash -s -- --version alpha

# 精确版本
curl -fsSL https://cdn.leagent.me/computer/install.sh | bash -s -- --version v0.5.0-rc.2
08 / 升级

不是覆盖一个文件，而是“验货 → 入库 → 接班 → 可回退”

按环境解析包源，或使用排障指定的精确版本Production 只读 stable；Test 只读 preview；然后得到不可变版本清单、平台下载 URL 和 SHA-256。
下载并双重验货先验压缩包 SHA；解压后再把候选 binary 的 SHA 交给 installer bridge 验证。
Stage 到 VersionStore版本二进制按不可变版本保存，稳定 launcher 路径不变。
激活新 Active，保留 Previous安装和 computer upgrade 走同一套 VersionStore，不再形成两套升级真相。
新 generation 接班新 resident 拿更大的 generation；服务端拒绝旧 resident 的迟到心跳和结果。
在线验收或回滚目标版本、successor、所有 runtime 收敛才算成功；失败则切回 Previous。

为什么 generation 很重要？进程 A 重启成进程 B 时，A 不一定马上死透。generation 像任期号：B 的任期更大，服务端看到 A 的旧任期就拒绝，避免两个 resident 同时报结果。

09 / 部署

正规目标：服务制品可提升，客户端包按稳定性分轨

目标契约

dev 自动部署腾讯测试服务并发布 preview 客户端；验收后，main/生产批准提升已验证的服务 digest，并发布 stable 客户端。两条制品链都必须记录 commit、版本、校验和。

当前事实

仓库目前只有 aliyun-dev Environment 和 Aliyun self-hosted runner，没有腾讯 runner，也没有独立的 test / production 受保护 Environment。

因此 #2497 不能靠改 YAML 假装完成；必须有真实基础设施、服务健康和 CDN/部署证据。

10 / 日常操作

用户真正需要记住的命令很少

# 连接正式 Workspace
multica setup /workspace-a

# 连接腾讯测试 Workspace
multica setup --environment test --test-url https://test.leagent.me /workspace-a

# 两边都 setup 过以后，随时安全切换
multica config use test
multica config use production

# 看当前环境、固定包源和两边保存的登录（不会打印 token）
multica config show

# 看身份、当前环境、包源、漂移和全部连接
multica computer status

# 做只读诊断
multica computer doctor

# 生命周期
multica computer start
multica computer restart
multica computer logs

产品文案统一说 Computer / Workspace connection。daemon 和 binding 只保留在内部兼容 API、数据库或代码标识里。
