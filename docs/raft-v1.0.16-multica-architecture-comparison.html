结论 / Executive verdict

Reuse

复用 Raft 的 process ownership

Computer 是 machine-wide single writer；每个 managed binding/server 的 child 承载真实 behavior，而不是 sentinel。

Do not copy

不照搬 per-server cardinality

Raft child = attached Server；Multica child = Workspace Execution Binding。权限与 fault domain 不同。

Target seam

Computer 与 daemon 分包

internal/computer owns Host policy；internal/daemon owns one Binding child's execution。

6. Machine Upgrade flow / 跨 child 升级

Current child forwards machine actionServer action 从 current Workspace Runner 到 Host；child 不自行 swap machine binary。
Computer Host prepares every current child通过 generation-fenced loopback control 调用 prepare。
Each child drains only its own executionclose claim barrier → graceful task cancel → bounded force termination of owned provider processes。
All prepared → stage / verify / replace任一 child prepare 失败，Host release 所有已经暂停的 siblings。
Successor rebuilds all children等待真实 Ready 与 Runtime reports，再做 machine generation / runtime attestation。

9. Broader architecture findings / 后续优先级

1

Agent lifecycle single owner — Strong

旧 Lifecycle Operation 与 Runner desired/observed reconcile 仍是 competing owners。应 hard cut 到一条 control path，不能再加 adapter 双写。

2

Machine lifecycle deep module — Implemented

upgrade/restart phase ordering、durable journal 与 successor attestation 已归 Computer owner；CLI 只保留 process-launch adapter。

3

Frontend Computer projection — Strong

把 build → merge pending → decorate → selection 收成一个 headless projection seam，减少 views 掌握 pipeline stages。

4

Mobile Presence parity — Strong

消费 canonical server snapshot + agent:presence delta；不要再从 runtimes/tasks/activity 推导 Presence。
