# s89 public IP HTTPS

## Goal

Provide a browser-trusted secure context at `https://82.157.184.89` so the
deployed web composer can access `getUserMedia` without weakening browser
security.

## Evidence and execution log

- [x] Confirmed `http://82.157.184.89:8090` is the user-facing Multica dev
  address and is not a secure context.
- [x] Confirmed `leagent.me` resolves to `101.200.210.144`, so it cannot
  validate a certificate for s89.
- [x] Confirmed ports 80 and 443 are free on s89 and the existing proxy already
  declares those exact host bindings.
- [x] Confirmed s89 has Caddy v2.11.3, which includes the completed public IP
  certificate support tracked by caddyserver/caddy#7399.
- [x] Confirmed Let's Encrypt public IPv4 certificates are generally available,
  require the `shortlived` profile, and support HTTP-01 validation.
- [x] Added a repository-owned Caddyfile that preserves HTTP `:8090` and serves
  trusted HTTPS for `82.157.184.89` with automatic renewal.
- [x] Added Caddy to the s89 Compose topology using its existing persistent
  certificate/config volumes.
- [x] Updated CD to install the reviewed Caddyfile, adopt the exact legacy
  container once, start Caddy after the app, and verify the trusted certificate.
- [x] Found the deployed public/app URLs still pointed at HTTP `:8090` and the
  blocked `leagent.me` host; the s89 override now changes cookies, callbacks,
  durable attachment URLs, and generated links to the HTTPS IP atomically.
- [x] Routed browser, daemon, and sandbox WebSocket upgrade paths directly to
  the backend; this removes the observed Next proxy failure
  `malformed HTTP status code "Server"` when daemon/sandbox clients reconnect
  through the new HTTPS public URL.
- [x] Pinned Caddy v2.11.3 by digest and extended the existing CI-executed
  self-host configuration test with the s89 HTTPS identity, ports, volume,
  short-lived profile, and WebSocket route contracts.
- [x] Added pre-replacement runtime validation and force-recreate only Caddy
  after atomically replacing its single-file bind source; the new container
  therefore mounts the new inode instead of reloading stale bytes.
- [x] Review found that serving the full UI on HTTP `:8090` while issuing Secure
  cookies would leave old bookmarks logged out and microphone-disabled. HTML
  navigations now redirect to HTTPS while daemon/API traffic stays available;
  CD verifies the redirect target before declaring the deployment healthy.
- [x] Review found the runtime Caddyfile was overwritten before validation. CD
  now validates the checkout source first and installs it with an atomic rename.
- [x] Disabled Google OAuth on the IP-only entrypoint. Enabling it requires the
  browser itself to use a DNS origin plus matching Caddy and registered callback
  configuration; changing only the backend fallback URI is insufficient.
- [x] Restricted the s89 backend host binding to loopback instead of inheriting
  the base Compose file's public `0.0.0.0:8080` binding.
- [x] Validated the Caddyfile with the pinned Caddy v2.11.3 image, rendered
  the merged Compose model with `scripts/selfhost-config.test.sh`, checked the
  workflow with actionlint v1.7.7, and ran `git diff --check`. An ephemeral
  pinned Caddy container returned `308` and preserved `/old/path?x=1` in the
  redirect to `https://82.157.184.89`.
- [x] Pushed `feat/s89-ip-https` and opened ready-for-review PR #951 into
  `dev`: <https://github.com/LRM-Teams/multica/pull/951>. The branch is stacked
  on deploy-target repair PR #948; its comparison contracts to this HTTPS
  change when #948 merges.
- [ ] After deployment, verify the public certificate, secure context, health
  endpoints, and microphone permission prompt.

## Boundaries

- No server file or container is changed directly; rollout occurs only through
  the reviewed CI/CD workflow.
- The HTTP `:8090` listener remains available for daemon clients and rollback.
- This PR does not change voice capture, ASR, TTS, or message UI code.
