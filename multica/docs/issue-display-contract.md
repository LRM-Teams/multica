## 2. 状态与优先级枚举（**服务端实证、不是记忆**）

### 2.1 status = 七个（`GET /api/issues?limit=200` distinct 查实）
```
backlog · todo · in_progress · in_review · blocked · done · cancelled
```
> **⚠️ `cancelled` 是双 L。** **CASE 拼错会静默漏掉一整组** —— 不报错、只是那组人间蒸发。

### 2.2 ★ 锁定的显示顺序（**离 done 近 → 远，完成/取消垫底**）
```
1. in_review   2. in_progress   3. blocked   4. todo   5. backlog   6. done   7. cancelled
```
**依据分级**：
- **`抄`**：**1 / 2 / 4 / 5 + done、cancelled 垫底 = Linear 逐字一致**。
- **`定`**：**`blocked` 排第 3 —— Linear 没有这个状态**（它只有 Backlog / Todo / In Progress / Done / Canceled + 自定义）。
  **理由**：①**起过头的活**（有上下文、比 todo 离 done 近）②**但不动**（所以排在 in_progress 之后）③**必须留在"活跃带"可见** —— **blocked 最需要人介入，埋到 backlog 底下 = 把最该被看见的问题藏起来**。
  > **可推翻**：若产品认为"blocked 该置顶抢注意力"，那是**按紧急度**的另一套语义、**就不是照 Linear 了、要明说**。

### 2.3 ⚠️ 排序必须在服务端 —— **服务端契约 `可执行`｜owner: @Ronan ✅ 已签；客户端禁重排仍 `仅文档`**（见 §5.3）
**对分页返回的部分结果做客户端排序 = 假的全局顺序**（第 2 页一来就崩）。

### 2.4 priority 枚举
```
none · low · medium · high · urgent
```

## 3. 引用（inline reference）

### 3.1 机制：**服务端 anchor 成 part、前端不搜文本**
- 服务端在 `parts[]` 落 `ref_id` / `label` / `content_start_utf16` / `content_end_utf16`；**前端按 span 投影**。
- **正文存干净文本、引用挂在旁路 span 上** → **正文不可变、历史不回改**。
- **⛔ 前端绝不用正则"认出"引用假装成 token** —— 那是 raft 的实现路子（前端猜），**不是我们的**。
  > **我们照抄 raft 的产品行为、不照抄它的实现**：`task #N` 可点、**裸 `#N` 不认**（raft 自己写明：**跟 PR/issue 号有歧义**）—— 但**我们的路子是 entity+span、更严、不倒退**。

### 3.2 ★ 正文不可变 / 实体状态一律现查 —— **`可执行`（已落地）**
- **`parts[]` = 锚 + 身份，仅此而已。**
- **status / assignee / priority / project = 一律现查**（`useResolvedIssue(ref_id)`）。
- **快照既不是渲染源、也不是 fallback** —— **"拿过期数据兜底比不显更糟"**。
- **为什么**：**3 天前那条消息的字，不该被今天的 issue 状态改写。**
- **可执行形态**：**`part.ref_status` 字段已从 payload 删除**（#507/#625）→ **没人能读到过期快照，因为快照不存在了。**
- **配套回归**：**write-then-mutate**（#622）—— **先发消息 → 再改 issue → 再 hover → 必须显新值**。
  > ⚠️ **这条测试是补上来的**：原 fixture **在回填之前就把状态设好 → 快照天然等于真值 → 测试永远绿、测不出陈旧**。**fixture 的时序本身能让一个测试变成摆设。**
- **★ Reader-first 顺序（本身就是规矩）**：**FE 先停止读 → BE 再删字段**（#622 → #507/#625）。**永远不能反过来。**

### 3.3 阅读面 vs 编辑面：**两个语境本来就该不一样**
- **正文（阅读面）= 零装饰纯链接 + hover 卡。** 读的时候你**不操作它** → **框/底色在这里是纯装饰、没有对应功能**。
- **编辑器（操作面）= chip 是对的。** 你**正在操作它**（整体删 / 移动 / 光标跳过）→ **那个框是"这是一个原子 token"的功能信号、不是装饰**。（Slack / Linear / Notion 全这么分。）
- **★ 这不违反"一处概念一个长相"** —— **"编辑中的引用"和"读到的引用"本来就是两个概念**。
  > **写下来免得以后有人当成不一致、又"统一"回去。**
- **✅ `可执行`｜owner: @Felix `已签`｜档位 **①②**（见 §0.2 梯子）｜`15d143eaa`(#639) + #638**
  - **形态（判据照 @Felix 原话，两半 scope 不同、必须分开写）**：
    - **`barrel 入口` = 全仓不存在**（`IssueChip` 已从 `issues/components/index.ts` 摘掉 → **编译期拦截**：`has no exported member 'IssueChip'`，**含 apps/***）；
    - **`深路径 ./issue-chip` = 唯一受控入口**，**仅 `packages/views` 内受 restricted-import lint 约束**（阅读态 projector 边界、**编辑器为显式例外**）；**apps/\* 直接深 import 不在覆盖内 —— 已知边界、非已知洞。**
  - **⛔ 这条曾被我标高又降档（同日 10:32）**：@Wren 查出 **barrel re-export 可绕过按 `./issue-chip` 写的 ban** → 它当时给的是**「部分保护 + 完整信心」**。**@Felix 摘掉 barrel（选 B）后洞消失 → 恢复 `可执行`。**
  - **⭐ 为什么 B 而不是"连 barrel 一起禁"**：见 §7.2.1 —— **A = 再列一遍路径（路径会长）；B = 让路只剩一条。** **升档代价 = 0**（barrel re-export 零消费者），**且 lint 例外清单反而更短了**。

### 3.4 兼容的是路径、不是外观
> **「兼容路径可以留，但不能长出第二副面孔。」** — @Felix
- 老数据的兜底**路径可以留**；**渲染必须与主路径并线**。
- **`可执行`｜owner: @Felix ✅ 已签、已落 PR #638**：两条路**渲染同一个组件**（**`IssueRefLink` = 正文里 issue 引用唯一的长相**：零装饰 + peek；**projector（锚定）和 linkify 兜底（没锚）都渲它**）→ **结构上没法长出第二副面孔**。
  > **「并线要并到同一个组件，不是并到同一份 CSS。」** — @Felix（实现层的准确形态）
  > **「"两边长得一样"从此是"只有一个组件"这个事实，不是两个调用点靠小心维持的承诺。」** — @Felix
  > **「外观一致不靠两边小心写得一样，靠结构上没法不一样。」** — @Felix

### 3.5 ⭐「猜」和「认」必须可分辨 —— **`可执行`｜owner: @Felix `待签`**
- **锚定路径 = 服务端认过的；兜底路径 = 前端正则猜的。** 外观并线后（3.4）**两者同一张脸**。
- **代价（写明）**：漏锚从「**显眼的 chip**」退化成「**隐形的不一致**」—— **前端的暴露通道是我们亲手关掉的。**
- **解法**：**`data-ref-source="anchor" | "fallback"`** —— **用户看不见、测试看得见**。
  > **「不让界面撒谎是对用户；对我们自己，界面反而必须说实话。外观并线、真相留痕。」** — @Felix
- **契约（jsdom 可跑）**：
  - 同一条消息同一引用出现 N 次 → **`data-ref-source` 全 `anchor`**；出现 `fallback` = **漏锚 FAIL**
  - **代码块 / 行内 code / URL 内**的 `LRM-xxx` → **不升级、无 token**（**服务端不会犯这个错、正则会**）
  - **兜底解析失败**（如 `LRM-9999` 不存在）→ **纯文本**（不可点 / 无卡 / 无 URI 裸露）。**锚定路径永远遇不到这个分支**（服务端已验过）、**只有兜底会**。
  - **`fallback` + 解析失败 = 正则误报**，与漏锚**同族**（一个**漏认**、一个**错认**）
- **⚠️ 拆迁日**：parser 修好（#521）→ 所有裸引用都锚定 → 兜底没活干 → **整条删、`data-ref-source` 一起删**（#463/#510）。**它是拆迁期的脚手架，别让它长住。**

### 3.6 降级铁律
- **无 entity/span → 纯可读文本 `@Label`**；
- **绝不露 `mention://` 或任何内部 URI**；
- **未知的 ref 类型 / status → 当纯文本、忽略** —— **不假渲、不瞎推**。

### 4.1 ★ 一个属性 = 一种语法 = `[标记] + [文字]` —— **`可执行`｜owner: @Felix `待签`（task #518）**

| 属性 | 标记 | 文字 |
|---|---|---|
| **status** | StatusIcon（状态语义色） | 状态词 |
| **priority** | PriorityIcon | 优先级词 |
| **assignee** | **头像（ActorAvatar）** | 显示名 |
| **project** | ProjectIcon / emoji（**不套 chip**） | project 名 |

- **来源 = `抄`（我们自家）**：**`list-row.tsx` 已经跑了几个月**（`ActorAvatar` / `ProjectIcon`+title / `PriorityIcon`）→ **这不是新规范，是把已在跑的写成强制**。**Linear / GitHub / Slack 亦同**（人的"图标"就是他的脸）。
- **规矩**：**每个属性都必须有标记**；**任何属性不套 chip/pill/底色**（chip 是"可点的实体"才配有的重量，**属性值不是**）。
  > **裸文字 assignee = 孤儿**：一行里三个有标记、一个没有 → 那个没有的会被眼睛判成"另一类东西"。**这是"乱"的机械来源** —— **不是间距问题、是语法问题**（所以挪间距治不好）。
- **`可执行` 形态**：**共享组件不给"裸文字 assignee"这个选项 → 就不可能画出孤儿。**
- **现状**：web **6+ 处各画各的**（list-row / board-card / issue-detail / gantt / inbox / hover 卡）；**mobile 早就抽了**（`attribute-chip.tsx` / `attribute-row.tsx`，其 CLAUDE.md 已写明这是 parity 隐患）→ **落后的是 web**。

### 4.2 ⚠️ 共享「语法」≠ 共享「显示策略」 —— **`可执行`｜owner: @Felix `待签`（API 形状）**
- `list-row` 的属性跟 **`storeProperties` 用户开关**走（Linear display properties）；
- **卡绝不继承那个开关** —— **"我在列表里把 project 关了，不代表 hover 卡该瞒着我这个 issue 属于哪个 project"**；
- **卡的规则永远是**：**设了就显、没设不占位**。
- **`可执行` 形态**：**共享组件只接"一个属性值怎样显示"，绝不接任何策略开关；「是否渲染」由各 surface 容器决定。**
  → **API 里没有那个参数，卡就不可能按列表开关撒谎。**

### 4.3 数值（**`定`、起点值，实测后可调**）
标记 `14px`（头像同 14px 圆形）· 标记↔文字 `4px` · 属性↔属性 `10px` · 文字 `12px`/muted · 卡宽 `320px` · 标题 `14px/600`、≤2 行尾截。
**属性行永远单行**，放不下按 **project → assignee → priority → status** 尾截 —— **status 永不省**（最常被瞄的那个）。

## 6. 依据分级（**写设计稿/定契约时强制**）

每条结论必须分：
- **`抄`** — 来自 Linear / GitHub / 我们自家 `list-row`（**注明出处**）
- **`定`** — 我们自己的选择（**注明理由**；无先例就如实说"没先例"）
- **`实测`** — `getComputedStyle` / 读到的代码行（**注明 file:line**）
- **⛔ `目测`** — **看截图猜的 → 不准进稿**（去量、或写「待测」）

**为什么要第三轴**：**一个数值可以既不是抄的、也不是我们定的，而是"我以为我看到的"。**
> **实例（本稿作者亲历）**：把**目测的「标题 17px 粗体」当成事实**写进稿 —— **真值 `14px`**。**2× retina 截图里 14px CSS 渲成 28px 像素、看着就像 17-18。**

**别把"我们的选择"说成"XX 就是这么做的"**：
> 例：**内联引用 hover 卡是我们定的** —— **Linear 的 peek 是列表里按 `Space` 的 quicklook、不是内联 hover**；**GitHub 才是先例**。**说成"Linear 就是这么做的" = 拿假权威压决策。**

## 7. ★★ 验证方法论：**验证装置本身会静默地让验证变成空转**

**四个实例、同一个毛病 —— 装置全都"看起来在工作"（绿的、跑了、有断言），但它什么都没测：**

| 装置 | 怎么空转的 |
|---|---|
| **fixture 时序**（#622） | 回填**之前**就把状态设好 → **快照天然等于真值** → 测试永远绿、测不出陈旧 |
| **`AppLink` 不透传 props**（#638） | `data-ref-source` **静默 no-op** → **验收建在不存在的东西上** |
| **测试 mock 吞了属性**（#638） | **断言变成测 mock** |
| **量到 wrapper 元素** | 得出「token 不是蓝的」的假结论（**真值在最内层 `<a>`**） |

### 7.1 ★ 铁律：**每个验证装置都必须先被证伪一次 —— 见过它红，才知道它会红**

> **「没人见过它失败的 lint，等于"我希望它存在"。」** — @Felix, 2026-07-16
> （他做 `no-restricted-imports` 时**故意把 import 加回去看它真报错、再撤掉** —— **这一步不是谨慎，是这条 lint 从"愿望"变成"可执行"的那一刻。没有这一步，它就该标 `仅文档`。**）

**→ 进 #522 标签规则**：**`可执行` 除了"指到具体的物"，还要 owner 确认"见过它红"。没见过它失败的装置 = `仅文档`。**

> **⚠️ 这条本身不够、见 §7.2.1**：**「见过它红」必须是「见过它对每一条已知入口都红」** —— 本稿写下它 10 分钟后就被 barrel 重导出打穿了。**规矩自己也会空转。**

### 7.2 ⚠️ 第五实例（**比前四个更阴**）：**允许清单发给会增长的那一侧 = 保证漂移**

**机制**：`files`-scoped lint（如 #638 的 `no-restricted-imports`，`files: [common/**, mention-card]`）= **允许清单**。
**将来新增一个阅读面 → 它不在清单里 → lint 不报错、也不保护 → 静默失效。**

> **前四个实例是"现在就空转"；这个是"以后某天开始空转，且没人会注意到那一天"。**
> **★ 它跟「见过它红」是配套的**：**你可以见过它红，但你见不到它"以后对新文件不红"。**

**→ 定则**：**看允许清单发给了哪一侧。**
- **发给"会增长的那侧"（阅读面）** → 新成员**默认没保护**、要有人**记得**扩 scope → **保证漂移**；
- **发给"有限已知的那侧"（editor + chip 定义 + stories）** → 新成员**默认有保护**、要**显式开口子**、而开口子会进 review → **稳定**。

**关键的不对称**：**例外清单是有限的、已知的；阅读面清单是无界的、会长的。**
> **这不等于"全局禁"**（编辑器操作态照样用 chip、在例外里）—— **只是默认方向反过来**。

**⚠️ 边界由 owner 拍**：反向 scope 是否噪音过大、有无别的合法 import 点（stories/测试），**实现方说了算**；**若判定不划算，如实标注"已知会漂移"** —— **别以"非阻塞"的名义悄悄留下**，因为**它失效的那天没有任何信号**。

### 7.2.1 ⛔ 第六实例：**「见过它红」≠「见过它对每一条入口都红」**（**这条打穿的是 §7.1 本身**）

**实例（同日、`no-restricted-imports`）**：
- owner **确实"见过它红"** —— 故意把 `import … from "./issue-chip"` 加回去、看它真报错、再撤掉。**照 §7.1 三要件，完全合格。**
- **但 barrel `issues/components/index.ts` re-export 了 `IssueChip`** → `import { IssueChip } from "../components"` **走的是另一条路，从来没人见它红 —— 它一直是绿的，而且是"应该红却绿"的绿。**

> **★ 一个装置可以在你测的那条路上完美工作，同时对另一条路完全不设防 —— 而它看起来跟"全都保护了"一模一样。**

**→ §7.1 修正（**必须连带改**）**：**「owner 见过它红」= 见过它对每一条已知入口都红。没穷举入口 = 没资格标 `可执行`。**

**→ 收口的两个选项，不是一类东西**：
- **A：连 barrel 路径一起禁** = **再列一遍路径**。**路径是会长的**（新 barrel / 新 alias / `../components` vs `@/…` / 重导出的重导出）→ **§7.2「允许清单发给会增长那侧」原样再犯一次**。
- **✅ B：把 `IssueChip` 从 barrel 摘掉** = **让路径只剩一条**（`./issue-chip` 一个受控入口，只有有限例外集走）。
  > **★ 这就是 @Felix 自己那句话用在 import 上**：**「外观一致不靠两边小心写得一样，靠结构上没法不一样。」**
  > **→ 入口唯一，不靠"禁掉所有别的入口"，靠"别的入口不存在"。**
  > **A 要求 lint 追上所有路；B 让路只有一条 —— B 之后 lint 反而更简单，只需守住那一条受控入口。**
- **合法 importer 是有限已知集**（@Wren 查实）：`issue-chip.tsx`(定义) + 编辑器俩扩展(`editor/extensions/issue-reference.tsx`、`mention-view.tsx`) + stories；**#638 之后 `issue-mention-card` 也不再 import 它**。→ **例外集有限 = B 可行、且不违反"编辑器仍可用 chip"的约束。**

### 7.3 hover / 真机验收：**先让它红一次**

**⛔ 反例（本稿作者亲历、#504）**：fixture **在回填前就设好状态 → 快照天然匹配 → 验收"通过"了，其实什么都没验。**

**正确流程**：
1. **先把 issue 改成一个"错的"值**（如状态改成 `Cancelled`）→ **hover → 卡必须显 `Cancelled`**；
2. **显对了**，才证明**卡真的在现查**（而不是碰巧撞上"快照 = 真值"）；
3. **再改回正确值 → hover → 显新值** → **这时候的 PASS 才是真 PASS**。

> **只做第 3 步 = 空转。**

## 8. 元规矩：**别拿没验证的环节当地基**

> **「当"这条假说解释不了不对称"时，先问"是不是我假设的那个环节本身有 bug"，别拿它当反证。」** — @Felix, 2026-07-16

**实例（同日、同一个 bug）**：小林一条消息里三个裸 `LRM-126`，**只有第三个长成了 chip**。
- 推理：「若是前端 linkify 兜底，**没道理只有 1 个被升级、另 2 个没有**」→ **那个"没道理"恰恰就是 bug 本身**（服务端 parser 漏锚了相邻的第三次出现，offsets `[436,443)` / `[444,451)`）。
- **拿"服务端不会漏"这个没验证的前提，否掉了本来正确的假说。**
- **另一条并行的错**：拿"那台是旧版本"的**版本假说当结论** → **差点去催人升级、方向完全错**。

**→ 定则**：**先拉数据再归因。同一条消息里两种渲染 ≠ 一定是写手的锅。**
