3. 数据怎么走

单一真相 · 代码里不再走 attachment_ids
1

Upload

POST 文件 → 得到 attachment_id

2

Tray

有序 pending；ready 才可发

3

Send parts

text + attachment parts，一次提交

4

Server

normalize · 从 parts 派生绑定 · 落库

5

Bubble

正文区 + 附件区 hydrate

旧的 attachment_ids：只是「把已上传文件绑到这条 message」的请求边车， 靠扫 markdown 是否还含 URL 拼出来。目标态：绑定只从 parts[].attachment_id 派生； 产品代码里删掉扫 URL / 发边车的路径。不必为了「拒绝」而专门 400——确保没有旧调用方即可。

4. 请求长什么样（只用最新）

Channel / DM / Thread 同一契约
旧路径（删掉实现）
// 不再维护：扫 markdown + 边车
{
  "content": "![a](url1)\ntext\n![b](url2)",
  "attachment_ids": ["…", "…"]
}
我们只实现这条
{
  "parts": [
    { "type": "text", "text": "去 s146 查一下…" },
    { "type": "attachment", "attachment_id": "<uuid-a>" },
    { "type": "attachment", "attachment_id": "<uuid-b>" }
  ],
  "client_message_id": "…"
}

允许仅附件、无字（Slack 纯文件消息）。 绑定从 parts 派生；读路径 parts + hydrate attachments[]。 Human / Agent 同一 shape。无双写。验收 = 仓库里没有旧聊天写路径，不是「服务端 400 表演」。

6. 怎么算做完

验收清单
  1. 粘图 A → 打字 → 粘图 B → 托盘 A|B 在一起，字只在正文
  2. 发出后气泡同样「文 → 成组图」
  3. Network 只有 attachment parts；绑定不靠 content 里的 URL
  4. 聊天侧没有扫 URL 拼 attachment_ids / 光标插图的旧代码
  5. 纯附件消息可发送
  6. Issue 评论内联图仍可用
